# 5 传输层

> **主线**：网络层把分组送到**主机**，可主机里跑着一堆进程 —— 究竟交给谁？靠**端口**。网络本身不可靠，可用户要一条准确无误的管道 —— 靠**连接**。==**端口解决"交给谁"，连接解决"送得对不对"**==。两个协议就是这对取舍的两端：UDP 只要端口，TCP 两个都要。
>
> 位置感：向上接第 6 章的应用进程；向下只用网络层的"尽力交付"，所以**一切可靠性都得自己造** —— 第 3 章那套滑动窗口在这里重新出场。

## 5.1 传输层的功能：进程到进程

**与网络层的分工**：

| | 网络层 | 传输层 |
| --- | --- | --- |
| 通信单位 | 主机 ↔ 主机 | ==**进程 ↔ 进程**== |
| 靠什么找 | IP 地址 | ==**端口**== |
| 可靠性 | 尽最大努力 | 可选（UDP 不管，TCP 保证） |

**端口**：==16 位==，标识**主机里的一个进程**。同一台主机上，不同进程靠端口区分。

| 类别 | 范围 | 说明 |
| --- | --- | --- |
| **熟知端口** | 0 – 1023 | 固定给常用服务，==考试重点== |
| **登记端口** | 1024 – 49151 | 给不常用的服务登记 |
| **动态（临时）端口** | 49152 – 65535 | 客户进程临时申请，用完就还 |

**套接字 socket**：`(IP 地址, 端口号)` 二元组 —— ==它才是一次通信的完整端点==。网络层看到 IP，传输层看到 socket。

**复用与分用**：发送方多个进程共用一个传输层 → **复用**；接收方传输层按端口把数据交回给对应进程 → **分用**。

> 记法：==端口是"门牌"，socket 是"楼栋 + 门牌"==。同一个端口号在两台主机上是两个毫不相干的东西。

**常见端口（背）**：

| 应用 | 端口 | 传输层协议 |
| --- | --- | --- |
| FTP | 21（控制）／20（数据） | TCP |
| SSH | 22 | TCP |
| Telnet | 23 | TCP |
| SMTP | 25 | TCP |
| DNS | 53 | UDP（区域传送用 TCP） |
| DHCP | 67（服务器）／68（客户） | UDP |
| TFTP | 69 | UDP |
| HTTP | 80 | TCP |
| POP3 | 110 | TCP |
| IMAP | 143 | TCP |
| SNMP | 161 | UDP |
| HTTPS | 443 | TCP |

**服**务用熟知端口等客户来连；**客户**进程用临时端口，==每一次通信都可能换一个==。

### 无连接 与 面向连接

- **无连接（UDP）**：发之前不打招呼。每个报文段独立，走哪条路、到没到，传输层不管。
- **面向连接（TCP）**：先握手建连接、再传数据、最后挥手拆除。==这里的"连接"是**逻辑**的，不是物理的== —— 中间的路由器完全不知道有这么一条连接。

## 5.2 UDP

**特点**（一句话：==不要连接，只要端口==）：

- **无连接**：随时发，不建连、不维护状态
- **尽最大努力**：不保证可靠、不保证按序，==错了就丢，不重传==
- **面向报文**：应用层给一个报文，UDP 加个头就发，==不合并不拆分== —— 报文边界被保留
- **首部小**：只有 ==8B==（TCP 是 20B）
- **支持**：一对一、一对多、多对一、多对多

**首部**：4 个字段，各 2B。

| 字段 | 作用 |
| --- | --- |
| 源端口 | 发送进程（不需要回信时可全 0） |
| 目的端口 | 接收进程（==必填==） |
| 长度 | ==首部 + 数据==的总长，最小值为 8 |
| 检验和 | 查错，==错了就丢== |

**检验和怎么算**：在首部前面**临时**拼一个 **12B 伪首部**（源 IP 4B ＋ 目的 IP 4B ＋ 全 0 1B ＋ 协议号 17 1B ＋ UDP 长度 2B），连同数据按 **16 位**一组做**二进制反码求和**，结果取反写进检验和字段。

> [!warning] 易错点
> 1. ==**伪首部只参与计算，不随报文发送**== —— 它存在的唯一目的，是把 IP 地址也拉进来一起校验（既然网络层不做校验和，就在这儿补上）。
> 2. ==**计算结果全是 0 时，检验和字段要填全 1**==（不是 0）—— 因为 0 表示"我没校验"。这是送分也送命的点。

**什么时候用 UDP**：==实时性 > 可靠性==的场合 —— 实时音视频、DNS、DHCP、TFTP、SNMP。丢几个包不影响听感，重传反而卡顿。

## 5.3 TCP 概览：段格式

**特点**：面向连接、==点对点==（不支持组播广播）、**可靠**（无差错、不丢失、不重复、按序）、**全双工**、==面向字节流==。

> 与 UDP 对照：UDP 面向**报文**（保留边界），TCP 面向**字节流**（边界被抹平）。==这就是"粘包"问题的根== —— 发 10 次收 10 次，也读不出边界。

**段格式**：固定首部 **20B**，带选项最长 ==60B==。

| 字段 | 长度 | 作用 |
| --- | --- | --- |
| 源端口／目的端口 | 各 2B | 找进程 |
| **序号 seq** | 4B | ==本段第一个**数据字节**的编号==（不是段号） |
| **确认号 ack** | 4B | ==期望收到的**下一个字节**的编号==；`ack = 已按序收到的最后字节 + 1` |
| 数据偏移 | 4b | 首部长度，==单位 4B==，故最小值为 5（即 20B） |
| 保留 | 6b | 未用 |
| **标志位** | 6b | 见下表 |
| 窗口 | 2B | ==接收窗口 rwnd==，告诉对方"我还能收多少字节" |
| 检验和 | 2B | 首部 ＋ 数据 ＋ **12B 伪首部**（同 UDP，协议号换 6） |
| 紧急指针 | 2B | 仅 URG = 1 时有意义 |

**六个标志位**：

| 位 | 含义 |
| --- | --- |
| **URG** | 紧急指针有效，数据优先送 |
| **ACK** | ==确认号有效==。连接建好之后，所有段都置 1 |
| **PSH** | 收到就立刻交给应用层，不缓存 |
| **RST** | ==重置连接==（出错、拒绝非法连接） |
| **SYN** | ==请求建立连接== |
| **FIN** | ==请求释放连接== |

> [!warning] 序号的两个坑
> 1. ==**序号按字节编号，不是按段**==。发 100B 数据，下一段的序号就 +100。
> 2. ==**SYN 和 FIN 各要占掉一个序号**==。所以握手里 `SYN = x` 之后，对方的确认号是 `x + 1`。

## 5.4 TCP 连接管理：握手与挥手

**三次握手**：

| 步 | 报文 | 方向 | 序号 |
| --- | --- | --- | --- |
| 1 | **SYN = 1** | 客户 → 服务器 | `seq = x` |
| 2 | **SYN = 1, ACK = 1** | 服务器 → 客户 | `seq = y, ack = x + 1` |
| 3 | **ACK = 1** | 客户 → 服务器 | `seq = x + 1, ack = y + 1` |

> ==**为什么要第三次**== —— 只有两次的话，一个**过期的旧 SYN**（旧连接请求在网络里绕了一圈才到）也能让服务器直接建连接、分配资源，而客户根本不认，服务器白等。==第三次让客户最后确认一句"我确实要建"==，服务器才敢真正分配资源。

**四次挥手**：

| 步 | 报文 | 方向 | 序号 |
| --- | --- | --- | --- |
| 1 | **FIN = 1** | 客户 → 服务器 | `seq = u` |
| 2 | **ACK = 1** | 服务器 → 客户 | `seq = v, ack = u + 1` |
| 3 | **FIN = 1, ACK = 1** | 服务器 → 客户 | `seq = w, ack = u + 1` |
| 4 | **ACK = 1** | 客户 → 服务器 | `seq = u + 1, ack = w + 1` |

> ==**为什么挥手要四次、握手只三次**== —— 握手时双方都"没有数据要带"，两个报文可以合并；挥手时服务器收到 FIN 后**可能还有数据没发完**，只能先回一个 ACK（"我知道了"），等数据发完再单独发 FIN（"我也关了"）。==中间这两步不能并，就多了一次。==

**TIME_WAIT**：==主动关闭方发完最后一个 ACK 后，要等 **2MSL** 才真正关闭==。两个原因：① 万一这个 ACK 丢了，对方会重发 FIN，我还得在才能应答；② 让本次连接的旧报文在网络中彻底消失，不去污染下一条四元组相同的连接。

**SYN 洪泛**：服务器收到 SYN 就分配资源 → 攻击者狂发 SYN、不回第三次 → 资源耗尽。防御靠 **SYN Cookie**。

## 5.5 TCP 可靠传输

**它与 3.4 的关系**：用的还是**滑动窗口**那一套，但==是 GBN 与 SR 的混合== —— 累积确认像 GBN，接收方能缓存乱序段像 SR。==注意 TCP 没有"接收窗口 = 1"这个限制。==

**两个重传触发**：

| 机制 | 做什么 |
| --- | --- |
| **超时重传** | 计时器到期还没收到确认，就重传 |
| **快速重传** | ==连收 3 个重复 ACK 就立刻重传==，不必干等超时 |

**超时时间怎么定**：取**加权平均往返时间**，再随波动自适应（$\alpha = 1/8$）：

$$RTT_S = (1-\alpha)\times RTT_S + \alpha\times\text{新样本}\qquad RTO = RTT_S + 4\times RTT_D$$

（$RTT_D$ 是往返时间偏差的加权平均。）

> ==**为什么不用固定超时时间**== —— 定太短会误重传（没丢也重发，白白加重拥塞）；定太长则丢包后干等。只能**边测边调**。

**快速重传怎么触发**：接收方收到**乱序的段**时，仍然重复确认**自己期望的那个序号**。发送方连收 **3 个**相同的 ACK，就判定"后面那段丢了"，立刻重传。

**接收方怎么处理乱序**：可以**缓存**乱序到达的段（这点像 SR），但**确认号永远指向"按序已收到的最后一个字节 + 1"**（这点像 GBN）。

> **MSS**：最大报文段长度，指一个 TCP 段里**数据部分**的最大长度（不含首部）。它由接收方在握手时通告。

***

## 5.6 TCP 流量控制

**目的**：==别把接收方的缓存冲爆==。手段是**接收窗口 rwnd** —— 接收方把"我还能收多少字节"写在每段的**窗口字段**里，发送方据此调整发送窗口。

> 位置感：与 3.4 的流量控制是同一件事，只是"帧"换成了"字节"。

**零窗口死锁**：接收方缓存满 → 通告 `rwnd = 0` → 发送方停发。等接收方腾出空间，本来会发一个 `rwnd > 0` 的报文，==但这个报文要是丢了，双方就互相干等==。

**解决 —— 持续计时器**：发送方收到零窗口通知就启动计时，到期主动发一个**零窗口探测**报文，逼对方把当前窗口再报一次。收到非零就恢复发送，收到零就把计时器重新归零。

***

## 5.7 TCP 拥塞控制

**先分清两个"堵"**：

| | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 谁堵了 | **接收方**的缓存 | **网络**（路由器队列） |
| 靠什么限 | ==接收窗口 rwnd== | ==拥塞窗口 cwnd== |
| 谁来定 | 接收方**通告** | 发送方**自己估** |

**四个算法**（==前两个一组，后两个一组==）：

| 算法 | 干什么 |
| --- | --- |
| **慢开始** | cwnd 从 **1** 个 MSS 起，每过一个 RTT **翻倍**（指数增长） |
| **拥塞避免** | cwnd 涨到 **ssthresh** 后改成每 RTT **+1**（线性增长） |
| **快重传** | 连收 3 个重复 ACK 立刻重传（见 5.5） |
| **快恢复** | 快重传后**不回到 1**，把 cwnd 直接降到新的 ssthresh，然后进拥塞避免 |

**转折点怎么走**（==画曲线就记这两句==）：

- **超时**（严重，可能丢了很多段）：`ssthresh = cwnd / 2`，==`cwnd = 1`，重新慢开始==
- **3 个重复 ACK**（轻度，只丢了一段）：`ssthresh = cwnd / 2`，==`cwnd = ssthresh`，直接快恢复==

> 一句话：==**超时 → 打回原形（cwnd = 1）；快重传 → 只砍一半（cwnd = ssthresh）**==。这是本节唯一的必考辨析。

***

## 5.8 发送窗口：两个上限与四段划分

发送窗口不是一个独立的量 —— ==它被**接收方**和**网络**两头顶着==：

$$\text{发送窗口} = \min(\text{cwnd},\ \text{rwnd})$$

**窗口内再分四段**（==考试画图照这个画==）：

```
[已发已确认] │ ←左边界 [ 已发未确认 │ 可发未发送 ] 右边界→ │ [暂时不能发]
```

| 段 | 内容 |
| --- | --- |
| ① 左边界**之外** | 已发送、已确认，可以丢弃了 |
| ② **已发未确认** | 已发出、等 ACK。==超时没来就得重传这一段== |
| ③ **可发未发送** | **可用窗口** —— 立刻能发出去的部分 |
| ④ 右边界**之外** | 窗口还没挪，暂时不能发 |

- **发送窗口大小** = ② ＋ ③ = `min(cwnd, rwnd)`
- **可用窗口大小** = ==只有 ③==

> ==这两个量的区别是本处最大的坑==：**发送窗口**是左边界到右边界的**总宽**，**可用窗口**只是其中**还没用掉的那一截**。发送窗口不变时，③ 发出去多少，它自己就缩掉多少。

# 6 应用层

> **主线**：传输层交下来两条管道 —— **UDP** 和 **TCP**。应用层回答的是：==人怎么用这张网==。就四件事：**怎么给机器起名**（DNS）、**怎么传文件**（FTP）、**怎么寄信**（邮件）、**怎么看网页**（WWW）。每一样 = 一个协议 ＋ 一组固定端口 ＋ 一条"谁主动、用几条连接"的规矩。

## 6.1 网络应用模型

| | **C/S（客户/服务器）** | **P2P（对等）** |
| --- | --- | --- |
| 角色 | 客户主动请求，服务器被动等 | ==每个节点既是客户又是服务器== |
| 资源 | 集中在服务器 | 分散在各节点 |
| 优点 | 管理集中、易维护 | ==可扩展性极好== |
| 缺点 | ==服务器是瓶颈，也怕单点故障== | 管理困难、安全性差 |

> P2P 的本质：把"一台服务器服务所有人"换成"所有人互相服务"。==用户越多，C/S 越慢，P2P 反而越快== —— 这句就是 P2P 的考点。

***

## 6.2 DNS：把域名翻译成 IP

**为什么需要**：人记不住 `142.250.72.14`，只记得住 `www.google.com`。==DNS 就是这台"翻译机"==，默认走 **UDP 53**。

**域名空间**：树状**层次结构**，从右往左级别降低。

```
根
└── 顶级域  .com / .cn / .org
    └── 二级域  google
        └── 主机  www
```

**四类域名服务器**（==按"谁知道多少"排==）：

| 服务器 | 知道什么 |
| --- | --- |
| **根域名服务器** | 只知道各**顶级域**的地址 |
| **顶级域名服务器** | 只管自己这个后缀（`.com`）下的域名 |
| **权限域名服务器** | ==真正存着某区域完整记录的==（一个区一个） |
| **本地域名服务器** | ==离用户最近的那台==，不属于域名树，但**查询都从它开始** |

**两种查询方式**（==必考==）：

| | 递归查询 | 迭代查询 |
| --- | --- | --- |
| 谁干活 | 被问的那台**替你把事办完** | 被问的**只告诉你"下家在哪"** |
| 用在哪 | ==主机 → 本地域名服务器== | ==本地域名服务器 → 各级服务器== |
| 类比 | "你去帮我办" | "你去找他" |

> ==**记这一条就够**：主机对本地域名服务器用**递归**（我只要结果）；本地域名服务器对外面各级用**迭代**（我自己一层层问）。==
>
> **高速缓存**：各级服务器都把最近查过的映射存下来，下次直接答 —— ==减少查询次数、减轻根服务器负担==。

> [!warning] 易错点
> ==DNS 默认用 **UDP**==（一问一答，快）。只有**区域传送**（主从服务器间同步整块数据）这种要求可靠的场合才用 **TCP 53**。

***

## 6.3 FTP：传文件

**最特别的地方**：==用两条 TCP 连接==。

| 连接 | 端口 | 生命周期 | 传什么 |
| --- | --- | --- | --- |
| **控制连接** | **21** | ==整个会话期间一直保持== | 命令、响应 |
| **数据连接** | **20**（主动模式） | ==每传一个文件，开一次关一次== | 文件内容、目录列表 |

> ==**为什么要分开**== —— 控制连接得一直听着命令，数据连接要传大块内容，两者节奏完全不同。分开之后，**传文件的同时还能继续下命令**（比如中途中断传输）。
>
> 谁主动：**控制连接永远是客户主动连服务器**（21）；数据连接看模式 —— **主动模式**由**服务器主动连客户**（20），**被动模式**由客户再开个端口去连服务器。==考试里记住"两条连接、21 + 20"就够。==

## 6.4 电子邮件：谁推谁拉

**组成**：用户代理（写信读信）＋ 邮件服务器（存、转发）＋ 协议。

**一封邮件的完整旅程**：

```
发件人 →[SMTP 推]→ 发件服务器 →[SMTP 推]→ 收件服务器 →[POP3 拉]→ 收件人
```

| 协议 | 方向 | 端口 | 干什么 |
| --- | --- | --- | --- |
| **SMTP** | ==**推 push**== | 25 | 发信，以及服务器之间转发 |
| **POP3** | ==**拉 pull**== | 110 | 收件人把信从服务器**取下来** |
| **IMAP** | 拉 pull | 143 | 收信，但==信留在服务器上==，可多端同步 |

> ==**一句话记牢：SMTP 只管"往外送"，POP3 只管"往回收"**== —— 收件人不能用 SMTP 取信，这是最常见的错项。
> POP3 默认取走就删，IMAP 保留在服务器 —— 这就是"换个设备就没邮件"和"到处都能看"的区别。

**MIME**：SMTP **只能传 7 位 ASCII 文本**，图片、附件、中文都传不了。MIME 在**不动 SMTP 的前提下**，把非 ASCII 内容**编码成 ASCII** 塞进去。==它是 SMTP 的扩展，不是新协议。==

***

## 6.5 WWW 与 HTTP

**WWW 的三块积木**：==URL（资源在哪）＋ HTML（怎么写）＋ HTTP（怎么取）==。

**URL 格式**：`协议://主机:端口/路径`，端口默认 80，可省。

**HTTP 报文**（==纯文本，可以直接读==）：

```
请求行：GET /index.html HTTP/1.1      ← 方法 + URL + 版本
首部行：Host: www.example.com         ← 一堆 "字段: 值"
空行
实体：                                 ← GET 一般不带，POST 带
```

**常用方法**：`GET`（取）、`POST`（提交）、`PUT`、`DELETE`、`HEAD`。

**两类连接**（==重点==）：

| | 非持久连接 HTTP/1.0 | 持久连接 HTTP/1.1 |
| --- | --- | --- |
| 怎么传 | ==每个对象都要新建一次 TCP 连接== | 一次 TCP 连接**传完所有对象** |
| 开销 | 每个对象一个 RTT 建连，==慢== | 省掉反复建连，快 |

> 算时延就靠这一条：**非持久连接**取 N 个对象 ≈ $2N$ 个 RTT（每个对象 1 次建连 ＋ 1 次请求/响应）。

**无状态与 Cookie**：HTTP 本身**无状态**（服务器不记你是谁），==Cookie 就是为了补上"记住你"== —— 服务器发一小段数据给浏览器，下次请求浏览器自动带回来。

**代理服务器（Web 缓存）**：==替客户存一份副本==。命中就直接给，不必去源服务器 —— 降低时延、减少链路上的流量。

**HTTP 与传输层**：HTTP 用 **TCP 80**（HTTPS 用 **TCP 443**）—— ==HTTP 本身不需要可靠，但它要的"完整、有序"正好由 TCP 白送==。
